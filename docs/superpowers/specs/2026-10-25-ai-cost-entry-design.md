# AI 成本录入与开销分析设计稿

日期：2026-10-25。状态：用户已确认主备顺序、可修改与确认保存流程；其余工程默认值为本次落地设计建议。配套实施计划与 UI 原型见 `docs/ai-cost-assistant-2026-10-25/README.md`。当前不包含正式功能代码改动。

## 已确认的产品方向

- 用户认为现有食材批次录入过于繁琐，需要以图片或自然语言完成日常记账。
- Claude API 是默认模型；DeepSeek API 只作为备用。
- AI 分析结果必须先展示，用户可以增删改明细，最后一键确认保存。分析本身不入账。
- LLM 用于理解成本输入、分类和解释实际开销。

## 方案选择

曾考虑按任务分工（Claude 识图，DeepSeek 文字 / 分析），以及主备模式。用户选择主备模式：图片、句子和开销解释均优先 Claude；遇到符合条件的服务失败，再用 DeepSeek 接手。同一请求不同时发给两家，不为了普通缺字段或金额歧义切换模型。

以下未由用户指定的细节均为工程建议，按明确标注的默认值设计，不代表用户已经确认实际付款、数量或业务口径。

## 日常页面

食材与用料页的首屏改为「AI 记成本」。保留现有五类食材、采购记录和可选的用料记录；批次、核算范围、换批等折叠到「详细用料管理」。收支总览的记支出入口也能进入同一录入流程。

用户看到三个区域：

1. 输入：「今天买了葱10块，肉碎32块，都付了」。提供输入框和「拍照 / 上传收据」按钮。
2. 结果：可编辑的日期、币种、付款状态、项目、分类、金额及总计。数量、单位、供应商和付款来源折叠，缺少这些不阻止普通记账。
3. 确认：「确认保存 RM42.00」。金额合计由程序随修改实时重算。保存成功显示新增记录，可查看原话 / 收据与更正入口。

一笔输入可以生成多项明细，用户可直接修改 AI 识别结果、增加遗漏项、删除非营业项目。修改金额时更新合计；重试识别不能静默覆盖用户已修改的内容。

缺少关键资料时只提示对应位置。第一版不采用聊天式连续追问，也不要求重新填写整张表。

## 最少确认资料

| 字段 | 默认 / 规则 |
| --- | --- |
| 项目名称 | AI 提取，用户可改；无法辨认时由用户填写 |
| 金额 | 必须有；人民币式“10块”在本门店上下文建议为 RM10，并清楚展示币种；不能猜不清的数字 |
| 日期 | 缺省用该输入创建时的门店营业日；相对日期依门店时区及输入时间解析并展示，可改 |
| 币种 | 本店默认 MYR；明确其他币种时提示处理，第一版不自动换汇 |
| 分类 | 五类食材或现有日常费用项目；无法确定则标「待分类」，用户可选择「其他」确认 |
| 是否已付 | “全部付了 / 赊账”等明确表达可预填；缺省待确认，保存前选择已付或待付 |
| 数量 / 单位 | 可空；不能伪造 1 份、1 kg、1 批来满足旧接口 |
| 付款来源 | 可填，可选未说明；不能默认说成钱箱现金或老板自付 |
| 供应商 | 可空；允许用户修改 |

数量完整不等于用户同意开始使用。普通保存只登记采购和可追踪的采购明细，不自动开封、不结束旧批，也不自动认定食材当天全部消耗。

“一键入库”在界面中表现为「确认保存」：有明确数量的食材可记录待用库存资料；只有金额的食材记入采购账和待补用量记录。两种情况都无需先进入复杂批次表单。日常费用只入支出账，不生成库存。

## 收据核对

- 第一版支持 JPEG / PNG / WebP 图片，单张收据可由多张连续照片组成。上限建议每次 5 张、每张 10 MB；过大的图片先提示压缩，长收据保留足够文字清晰度。
- 提取商家、单号、日期、币种、商品名称、数量、金额、折扣、税费、总额及原文证据。无法辨认的字段保留空值和原图，不用另一模型的猜测填上。
- AI 的结构化结果仍须服务端校验；结构合法不等于事实正确。
- 保留收据打印总额用于核对。保存的明细（含用户确认的折扣 / 税费分摊或调整项）须与确认总额一致；不一致时提示差额，不能偷偷改金额。
- 一张收据可创建多条账本明细，但父采购单 / 收据总计仅作汇总，不再作为一笔支出叠加。
- 第一版允许识别“煤气、杂费”等现有费用；租金、电费仍遵循按月及重复付款规则。新增开档投入需在结果中明确选择，不能靠模糊文字自动改变回本目标。退款、更正旧账不自动执行，转入已有对应流程。

## 主备模型

优先 Claude，输出统一的 CostDraft JSON 结构。DeepSeek 实现相同结构和字段含义，模型名称由后端配置；选用当前支持图片输入的 DeepSeek 模型。

可切换条件：网络失败、限流、服务端错误、超时，或一次有限重试后仍无法产生合法结构。总重试次数、总耗时和输入上限必须受控。默认设计为最多一次主模型重试、最多一次备用模型请求，总处理时限由实现者在 Functions 请求时限内配置并记录。

不切换的情况：用户没提供金额 / 付款状态、原图模糊、费用分类不明确、账单不平、重复收据、关账限制。这些返回草稿待编辑或业务说明。密钥 / 权限错误记录为配置异常；备用已配置时可接手，但后台必须提示主模型需要修复。

两家都失败时保留输入 / 图片，提供重试与手动录入，不写入半笔账。用户不需要在普通录入页面选择模型。

## 保存和账务衔接

建议新增 AI 草稿与一次性确认命令，沿用现有老板权限、runCommand、金额 sen 整数、审计及关账约束。

1. 服务端校验老板与门店权限，建立识别任务并留存输入。
2. 在 Firestore 事务外调用模型，校验结构并保存 AI 原始草稿及模型来源。任何模型调用都不能放入可能重试的 Firestore 事务。
3. 用户编辑结果，保存草稿版本。
4. 确认提交时，服务端只校验用户确认的版本，不再次调用模型“改写”用户资料。
5. 同一事务写入已确认采购单、所有账本明细、可选库存资料、审计和草稿已入账标记。任一明细失败则整单不落账。
6. draftId + revision + operationId 共同约束一次性保存；换一个 operationId、刷新、重复点击或响应丢失也不能把同一草稿再入一遍。已保存草稿走更正流程，不重新确认。

旧的 recordIngredientPurchase 强制数量、单位和付款来源，不能直接拿它拼造数据。第一版应增加适配快速采购的写入能力，或抽取共用的事务写入逻辑。不得通过逐个调用已有 Callable 来“批量保存”，以免半成功或重试重复。

付款来源需要扩展「未说明」，同时检查账本、类型、命令校验、CSV、旧现金视角的兼容；未说明不视为钱箱付款。数量未知用独立的待补采购资料表达，已有 BatchDoc 保持数量为正的约束；以后补建批次必须关联原 expenseId，不能再创建支出。

快速记账不代表成本覆盖已经完整。尚未建立使用资料的采购不能凭空变成准确消耗、单份成本或已校准利润；采购开销分析始终可用。

## 数据与权限

- aiCostDrafts：输入来源、原文 / 私有图片引用、模型原始结果、用户修改结果、版本、状态、模型来源、最终账目 ID。
- 识别状态：待处理 / 处理中 / 待核对 / 失败；用户保存后的业务状态：已入账。取消草稿不影响既有账目。
- 每个模型尝试独立记录服务商、模型、耗时、token 用量和错误类别，不在普通日志中保存密钥或整张收据。
- 图片存入门店隔离的私有 Cloud Storage；当前项目尚未配置收据上传，实施时需补 Storage、上传限制与权限规则。浏览器不能公开共享收据链接供模型下载；后端验证文件归属后读取并传给模型。
- Claude / DeepSeek 密钥由后端 Secret Manager 管理，不进入 VITE 变量、前端 JS、可读 Firestore 配置或普通聊天内容。第一版由部署维护者配置，前台不增加密钥管理表单。
- 只有老板可识别、读取、编辑、确认及分析成本资料；模型无权执行账本写入、关账、退款或改目标。
- 收据文字仅作为待提取数据，不能作为执行指令。所有账目、查询范围与可执行操作由服务端白名单决定。

## 重复与恢复

图片哈希识别相同附件，结合商家 / 单号 / 日期 / 总额提示疑似重复。相似金额不直接删除记录；用户可确认确为另一笔采购，并保留说明。

任务和草稿在服务端持久化；断线重进先查询已有任务结果，不重复付费请求。超时任务标失败可手动重试。草稿修改使用版本校验，两个页面不能静默覆盖对方。

保存成功但前端没收到响应时，通过草稿状态或 operationId 查询最终账目。已关账日期按现有更正流程处理，不自动挪到今天、倒填或解锁。

## AI 开销分析

首期提供「这个月花在哪」「比上月多花在哪里」「有哪些待付款」三个快捷问题，也接受限定成本领域的文字问题。

服务端先按统一账本口径计算日期范围、已付 / 未付、分类金额、采购频次、环比和可核实的单位采购价。LLM 接收计算结果和必要的记录引用，生成解释，不负责自行合计金额或自由查数据库。

分析答案显示统计区间、资料完整性和可点开的账目依据。没有数量只讨论采购金额，不能把采购增加说成涨价；没有销售 / 消耗数据不推断损耗或单碗实际成本。示例问答不得成为真实报表数据。

分析缓存按门店、范围及账目版本失效；记录增删改、付款或归属变化后重新计算。后台设置调用额度和频率限制，不对每次页面刷新重复调用模型。

## 实施边界与验收

首期范围：图片 / 文字录入、Claude 主用 / DeepSeek 备用、可编辑结果、一键确认、采购记录及来源回查、基于账本的开销分析。语音、自动入账、自动换批、自动执行建议和完整库存预测留待后续需求。

最低验收场景：

1. “今天买葱10块”可在不填数量、单位或付款来源的情况下，确认付款状态后保存 RM10；不生成伪造数量。
2. 多项句子能编辑 / 删除 / 新增明细；保存结果严格等于用户最终确认内容。
3. 收据折扣、税费、合计差额可核对；同一收据不重复计总额。
4. 主模型正常时不调用备用；可重试的服务失败才有限切换；缺字段不会循环调用模型。
5. 重复确认、跨页面确认、响应丢失和同草稿更换 operationId 均只入账一次。
6. 一张单据中某项触发关账或固定费用重复规则，整单拒绝，不留下已保存的一半。
7. 后补批次和启用库存不新增采购付款；旧批和历史记录保持可用。
8. 成本未完整时不显示准确利润；开销分析金额与账本逐项一致，缺少数量时不声称单价上涨。
9. 收据与草稿不能被其他门店 / 非老板读取；前端包和日志不包含 API Key。
10. 手机操作在输入、核对、保存三步内完成；常用路径不强制打开批次和高级资料。
