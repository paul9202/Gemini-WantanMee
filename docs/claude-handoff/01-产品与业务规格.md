# 01 · 产品与业务规格

## 1. 要解决的实际问题

收银员在高峰期快速且准确地下单；包括不懂中文和英文的员工，可通过餐品照片、选项图卡和示范培训操作；头手站在约1.5米外看懂要做什么；老板能把收到的钱、食材消耗、支出和出餐速度核对清楚。系统还要诚实反映订单在哪个设备、是否已同步、厨房是否收到。图片契约见06，不能仅交付文字中英切换。

成功标准：默认单碗从选择餐品到进入收款不超过4次有意义点击；改面薄多一次图卡选择；实际员工通过06场景测试；常用触控操作即时反馈；网络正常时跨设备同步在实测目标内；断网重启浏览器后订单仍在；重连不漏账、不重复收款、不重复制作。具体测量见04。

## 2. 角色、范围与权限

| 角色 | 日常工作 | 不允许 |
|---|---|---|
| Owner 老板 | 全部经营数据、价格/BOM、日结、支出、退款、设备与成员 | 无审计地删除交易或改写已关账历史 |
| Cashier 收银 | 指定主收银设备点单、现金/QR确认、餐牌回收、补单、查看订单和交班信息 | 修改 BOM、看老板成本利润、正式退款、创建成员 |
| Kitchen 后厨 | 看厨房投影、开始制作、出餐、限时撤回、确认异常 | 读取售价、成本、支付流水、老板报表 |

老板个人账号优先 Google 登录；员工使用受邀的独立 Firebase Auth 邮箱账号，或老板配置的专用后厨账号。禁止开放注册后自动授予员工权限，禁止靠前端隐藏菜单实现授权。共享设备进入锁屏后遮挡业务信息；锁屏 PIN 仅是本机便利控制，不是服务器身份认证。

首版只允许一个指定主收银终端产生新订单。其他老板设备不能同时接单；老板切换主机需联网并处理未同步日志。这样缩小断网时餐牌争抢的范围。误开第二个标签页用跨标签锁阻止写入；不要把浏览器锁当作安全边界。

## 4. 菜单与规则矩阵

餐品用四个稳定的 `productKind` 表达；汤面不再依靠「面条 + soup 酱料」间接推断。

| 餐品 | 规格及基础售价 | 面/云吞 | 酱料 | 辣度/油渣 | 加料 | Kosong |
|---|---|---|---|---|---|---|
| `dry_noodle` 招牌干捞面 | 小700 / 中900 / 大1100 sen | 1/3、1.5/3、2/4 | 黑/白/红 | 可选 | 叉烧+200；云吞3粒+200 | 可选 |
| `soup_noodle` 云吞汤面 | 小700 / 中900 / 大1100 sen | 同上 | 不出现 | 不出现 | 叉烧+200；云吞3粒+200 | 可选 |
| `dry_wanton` 干捞云吞 | 10粒700 / 15粒1000 sen | 0/10、0/15 | 黑/红（依餐牌） | 可选 | 云吞3粒+200 | 不可选 |
| `wanton_soup` 鲜肉云吞汤 | 10粒700 / 15粒1000 sen | 0/10、0/15 | 不出现 | 不出现 | 云吞3粒+200 | 不可选 |

全品类可选正常葱 / 多葱 / 走青。默认：小碗或10粒、黑酱、普通辣、正常油渣、正常葱、无加料；汤品所有不适用字段使用 `null`，不把隐藏值留下参与后厨或成本判断。

菜单更新依据：用户2026-10-22明确采用所附餐牌。两类面条均可选 `noodleType=thin_egg|mee_poh`（细面/面薄），默认细面，同尺寸售价一致，面球/份团数量一致；无面条的云吞餐品此字段为null。面薄单位成本尚无独立报价，首版暂沿用每份团85sen估值并在老板成本页标注待实店校准。KDS必须显示对应粗细面图片和两种面分开的待下锅数量，不能只有面条总数。

**Kosong 的新统一决策**：仅面条可选，基础价严格半价，小350 / 中450 / 大550 sen；云吞与叉烧均为0，两个肉类加料均禁用。开启时清除已选肉类加料；关闭时不自动恢复。此处有意修正原型「净面可加云吞却提示严禁云吞」的冲突；如老板以后要求净面配独立云吞，须另加一行云吞餐品，不能暗中改变Kosong定义。

**打包免汤的适用范围**：干捞面/干捞云吞打包时「不附送清汤」；云吞汤面与云吞汤本体必须含汤。不能把汤品打包做成无汤。所有打包餐品每份计包装成本20 sen，默认不向客人另收包装费；2份即40 sen。改为收费需要明确显示收费行和价格版本。

成本初值：每面球85 sen，每云吞22 sen，每标准叉烧份120 sen，酱菜油50 sen，云吞汤底配料60 sen，加叉烧120 sen，加3云吞66 sen。汤面首版沿用原型「面球+云吞+叉烧+综合底料50 sen」估值，独立汤底成本以后按配方修订，禁止无依据重复加底料成本。正常/多葱、多油渣首版不额外收费，综合底料仍用估值；页面明确提示尚未精细核算。

财务计算内部用 **0.1 sen 的整数成本单位**：每面球850、云吞220、叉烧1200、综合底料500、包装200。1.5面球成本1275，避免过早舍入1.275元。售价、付款、找零用整数sen。订单成本先乘数量再求和；最终显示 RM 两位、half-up 舍入，汇总底层保留精度。

## 5. 点单与收款

### 5.1 常规流程

1. 默认堂食，选当前可用餐牌；餐牌只建议、不在浏览菜单时抢占。
2. 选四类餐品之一，默认配置可以「加入本单」；尺寸、酱料在同一画布，特殊要求按需展开。每次加入后特殊选项归默认，防止上一位顾客的走青或 Kosong 残留。
3. 完全相同配置与备注自动合并数量；点击购物车行重新编辑；减到0提供短暂撤销。切换就餐模式应用整单并重算包装，购物车和厨单一起更新。
4. 点「收款 RM …」进入收款面板，先检查餐牌、配置与本地可写资格。
5. 现金输入实收，少于应收不能确认；显示找零。QR 显示档口二维码与应付金额，由员工核对自己的收款端到账后勾选确认。顾客截图不作为系统自动到账证据。
6. 员工点「确认收款并接单」，先将稳定ID与完整操作写入 IndexedDB；在线再向服务器提交。按钮禁用防连点，网络未知期间显示「正在核对接单结果」。
7. 云端提交成功才显示「云端已接单」；厨房终端真实确认后显示「后厨已收到」。成功提示音分别对应本机接单和后厨收单，不能提前播放误导。
8. 草稿从工作区移走后仍能在订单/同步中心恢复。新单建议循环查找下一个可用餐牌，50后回1；全满时阻止正式接单，提示先回收餐牌。

现金已收但请求失败/超时：在本机订单标「已收款，结果待核对」，保留同一 `clientOrderId` 和 `operationId` 重试；不让员工再次收钱。服务器实际已成功时重试返回原订单，不生成新流水。若顾客最终离开，应走取消和真实退款确认。

首版不做拆单支付、赊账、混合堂食打包、部分退款、临时任意改价或折扣；需要这些行为时先补规格。

### 5.2 餐牌生命周期

`available → held(orderId) → awaiting_return → available`

- 堂食和打包共用1–50；一个餐牌最多关联一张未回收订单。
- 在线接单事务同时占牌；本机离线日志同时在 IndexedDB 事务内占牌。
- 「已出餐」只把餐牌标为待回收，不自动释放实体牌。
- 收银明确点「餐牌已收回」才释放；未出餐不能普通回收，需先取消或老板异常处理。
- 取消订单将牌标为待回收，也要确认实体牌是否收回才释放；不以删除订单代替回收。
- 后厨撤回出餐只允许30秒内、原订单仍持有原牌、未关账、版本匹配；牌已回收或给了另一单时拒绝，说明原因。

## 6. 出餐与后厨

订单制作状态：`queued → preparing → served`；`queued/preparing → cancelled`。取消需要原因；制作中的取消需要后厨确认停止制作和食材处理。已出餐整单退款不改成取消，保留真实出餐历史。

默认 FIFO：`acceptedAtEffective` 早的在前，相同时间用稳定ID。原交接「等候时间升序」存在歧义，新规格明确 **等得最久的排最前**。

顶部分清楚「待下锅」与「制作中」；待下锅合计只统计 `queued`，开始整单制作后移到制作中，避免同一份再抓一次。首版按整单开始/整单完成，不做分行部分制作；厨房一旦点开始，应一次处理整单。底层预留行ID，但不做锅次分配功能。

待下锅：细面份团、面薄份团、面条总份团、云吞数、黑酱/白酱/红酱份数、汤面份数、云吞汤份数、Kosong份数。干捞面和干捞云吞的酱料可合计，但可展开看品类；Kosong是额外标记，不再加到总份数一次。细面与面薄须配原料图分栏，避免抓错面。

卡片以「餐牌 / 堂食打包 / 等待 / 餐品×数量 / 特殊要求」为阅读顺序。只强调偏离默认的要求；汤品显示「原汁汤底」，不出现「不辣/无油渣」。备注是纯文字，最长80字，不允许HTML。

云端后厨确认：KDS 接收到非缓存 ticket 后调用确认接口，服务器写 `kitchenAckAt`；它只说明设备收到，不说明厨师已经开始。5秒未确认显示「等待厨房确认」，15秒且心跳过期显示醒目异常，可选人工交接。阈值是产品默认值，可配置；不是 Firebase SLA。

耗时从接单到出餐，不从打开页面开始：正常 `<8分钟`，提醒 `8≤t<12分钟`，超时 `t≥12分钟`。分析分桶：极速 `<4`，正常 `4≤t<8`，偏慢 `8≤t<12`，超时 `t≥12`；8分钟达标定义为 **t<480000ms**。判断使用原始毫秒，不用四舍五入后的分钟数。

Undo 恢复原状态及原接单排序；重复点击幂等。所有设备看到一致结果；完成、撤回、取消冲突时按版本拒绝过期操作，客户端刷新并解释。

## 7. 离线营业：指定单机、本地持久化、人工传单

这是用户已确认的首版要求，不得降级成只能保存购物车。

### 7.1 开档准备

主收银联网登录，下载菜单/规则版本、营业日、餐牌与当前订单快照、角色和设备资格；完成「离线可用检查」。将壳、必要本地字体和静态资源缓存。本机有独立 `registerId`、设备epoch、持久化递增序号；跨标签只允许一个写端。身份过期不影响本机已经授权营业班次内的离线现金接单，但补同步必须重新通过云端认证。

首次从未联网初始化的浏览器不能凭空离线开档。刷新/重启能恢复已下载应用和本机已提交订单；用户清除站点数据、私密模式或设备损坏无法提供同等保证，交班页要显示本机待同步数并提供恢复包导出。

默认离线营业资格限已开启的一个班次，最多24小时；超时进入人工纸单模式并提示老板处理，仍允许查阅和导出已有订单。此时不得伪造云端授权。

### 7.2 断网操作

- 页头固定横条「离线营业 · 仅本机保存 · 未同步 3 单」；明确「后厨屏不会自动收到，请人工传单」。
- 现金正常收款并生成 `O-{registerShort}-{localSequence}` 临时展示号；实体牌仍是1–50。订单ID使用随机UUID，与展示号分离。
- 收款、订单、餐牌占用、日志同一 IndexedDB 事务提交成功后，才显示「本机已接单」。存储失败不得清空购物车或声称成功。
- QR 默认阻止核验；只有员工确实用另一台已联网收款设备确认到账，选择「已通过收款端核实」并记录说明，才可标人工已收。不能假定离线扫码等于到账。
- 每单显式选择/记录人工已交接；收银可记「人工已出餐」和实体牌收回。普通离线终端不能做正式退款、改价、改BOM或日结。
- 本地打印若已有可用系统打印环境可以尝试，但 Web 打印失败不影响本机接单；打印与重打均标识临时号及副本，不能依赖打印完成才保存。

### 7.3 恢复网络

先显示「恢复中」，保留本地数据。上传稳定的逐条日志到云端收件箱，按设备序号顺序应用，逐条记录已接纳/待核对/失败。只能在服务器确认后改为已同步，不能因为浏览器 `online` 事件就显示完成。

**所有离线订单保持 `kitchenRouting=manual`。** 人工已做完的导入为已出餐，不进入待做KDS；尚未做完的进入独立「人工单待核对」列表，不在主队列自动重发。需要转电子厨单时，由收银核实厨房未制作后明确操作，后厨收到醒目标识并确认。重连不自动打印、不再次收款、不重复播放新单提示。

重复上传返回原映射；改菜单后离线成交仍按有效的缓存历史价入账，并提示使用旧菜单。主设备被老板切换、牌冲突、菜单无法验证、日志缺号、设备时间异常时，进入云端待核对，保留已收金额和原始餐牌，不静默换牌/改价/丢单。其他合法订单按依赖条件继续或明确阻塞原因，老板能看到未入账金额。

离线使用设备估计时间；补入时间独立存 `cloudReceivedAt`，不能把它当点单时间。不能可靠验证的订单从出餐SLA样本排除，并显示样本数量；财务仍记录实际收款，时区/营业日异常待老板确认。

## 8. 订单修改、取消和退款

未收款草稿可任意编辑。收款接单后首版禁止直接改行项目、价格、付款方式；错误单以取消/退款后新开单处理，前后订单互相引用。

- 待做取消：立即从待下锅移除，标记应退款待处理；若没有消耗食材，反转分配的理论成本。
- 制作中取消：卡片保留「取消待确认」，后厨确认后终止；食材已消耗的成本保留，相关报废只做关联说明不重复扣。
- 已出餐退款：保留出餐与耗时，减少净收款，食材成本保留。
- 退款由老板实际退现金/QR后确认记录，记录金额、原支付方式、实际退款方式、原因、操作者与时间。首版仅整单全额；点击按钮不会自动划转银行资金。
- 不用 `cancelled` 状态直接推断钱已退；付款与制作状态独立。

## 9. 老板报表与财务口径

### 9.1 时间与数据完整度

档口使用 `Asia/Kuala_Lumpur`。营业日切点默认04:00；例如2026-10-23 03:59属于2026-10-22营业日，04:00属于新营业日。切点只对未来班次生效。

「今日」为当前营业日；「近7天/近30天」为含今日的7/30个营业日，边界半开 `[start,end)`；对比上一个等长区间。订单、退款、支出、损耗分别按对应事件的营业日筛选。跨日退款属于退款发生日，订单留在原售出日；明细可追溯。

所有图表显示统计区间、最近云端更新时间和「未同步/待核对」金额。零订单时达标率、均值、同比显示「—」，不能显示100%或假造50/50支付比例。

### 9.2 两本视角，避免进货重复扣成本

**经营视角（估算）**：

`净收款 = 已确认收款 - 已确认退款`

`估算经营利润 = 净收款 - 已分配理论食材及包装成本 - 未重复计算的报废损耗 - 固定费用摊销 - 其他营业费用`

按已收款接单分配BOM；待做未耗材取消时反转成本，制作或已出餐成本不反转。制作中已消耗项目取消的报废不能再扣同一份成本。经营指标属于管理估算，未覆盖工资/税费等成本时，展示「未包含项」，不宣称真实净利。

**现金视角**：

`经营现金净流入 = 实际收款 - 实际退款 - 已付进货 - 已付营业费用`

此处不再扣一次BOM或摊销；老板投资和提现另列资金往来，不是营业收入/成本。进货登记不等于盘存精确耗料。首版不做加权库存会计。

固定费用默认月度90000 sen，按该月日历日摊销，包括休息日，精确分配到sen：31天月份前7天2904 sen、后24天2903 sen；总和严格90000。不沿用「月900、每日34.60、近7天乘6」混用。老板可选营业日分摊模式，但需明确当月营业日表并保证总和；上线首版用日历日模式即可。

录入已付房租时，现金账减少900元；经营账仍按当月摊销，不能再把付款全额作为额外经营费用。支出分类为进货、固定费用付款、其他营业费用、资本设备；每条有应计归属与付款状态，避免重复。

### 9.3 回本

初始投入550000 sen为可配置初值；真实历史期初累计经营结果默认为0，不沿用演示1920。

`累计估算经营结果 = 经老板确认的期初余额 + 所有日期的估算经营利润`

`回本比例原值 = 累计估算经营结果 / 初始投入 × 100%`

进度条视觉范围0–100%，但数字允许负值/超过100%；亏损不被 `max(0,profit)` 吞掉。`待收回 = max(0,初始投入 - 累计经营结果)`。初始投入为0时显示不适用。名称用「按估算利润的回本进度」，与现金回收区别。

### 9.4 出餐分析

仅统计有有效接单/出餐时间、时间质量合格、实际已出餐的订单；退款但确实已出餐的仍算服务样本，取消未出餐不算。展示平均、中位数、P90、最快/最慢、堂食/打包对比、8分钟内达标率，以及极速/正常/偏慢/超时分布。所有值带样本数；P90采用nearest-rank `ceil(0.9*n)`；无样本返回null。

预计等待首版只提供「估计范围」：最近20笔有效出餐间隔的中位数 `c`（分钟，限制0.5–5，少于5笔用2）；`p=queued+preparing单数`；`E=max(3,2+c*p)`；区间 `[max(2,floor(0.8E)),ceil(1.3E)]` 分钟。有厨房离线、人工单未确认、时间异常时隐藏并写「暂无法估计」。此模型按整单吞吐估计，不声称能精确反映大单/锅次；保存算法版本，后续可根据面球/云吞量校准。

## 10. 进货、损耗与日结

进货保留原型快捷模板，但每次须确认实际金额、数量/单位、供应商或备注、是否已付、现金/银行及是否从钱箱支付。禁止模板点击即记账。交易不硬删除；错误记录作废并关联更正。

损耗允许0.5面球步长、整数云吞，必须大于0，原因选煮烂/掉落/剩余/其他。保存当时BOM版本；关联订单取消损耗时系统自动识别已计成本并显示「仅记数量，不重复扣款」。

日结步骤：检查未出餐和未回收餐牌 → 未同步及冲突清零 → 盘点钱箱 → 核对QR → 登记损耗 → 查看收支差额 → 老板关账。未完成订单可明确结转，保留原营业日；需要说明并列出清单。

`钱箱应有 = 开档备用金 + 现金收款 - 实际现金退款 - 从钱箱付出的支出 + 补入现金 - 存入银行/取走现金`

QR独立显示确认收款、退款、银行端核对额与差额，不能算入钱箱。不替银行确认到账。现金差额允许带原因关账，不要求伪造一致。

日结快照含版本、汇总、明细校验、操作者、时间、未完成事项；冻结后不改原快照，新增更正/重述版本。离线漏单迟到落在已关账日时，先记「关账后待调整」，老板以审计更正形成新版本；不得静默更新旧导出。

导出UTF-8 BOM CSV：汇总、订单、支付退款、支出、损耗、日结差额分别文件；货币列以sen或明确RM单位，时间含时区。自由文本防CSV公式注入。Google Sheets自动投递与Excel格式放到后续阶段，不阻塞首版。
