# 06 · 图片优先：不懂中英文的员工也能学习操作

本文件来自用户新增要求：系统将由不懂中文和英文的员工操作。用户随后确认首版「中文和图片为主」，以及菜单以所附餐牌为准：细面/面薄，小RM7、中RM9、大RM11。本文件与01/02共同构成v2.1设计基线。

## 1. 设计原则

常用任务采用「实物图片＋数量/金额数字＋短中文」；图片承担识别，中文供老板培训和辅助核对。英文保留设置，不在每张卡并排增加文字。语音、其他语言包可以扩展，首版不强制实现，也不能因此推迟图片操作。

图片不天然等于人人都懂。采用员工见过的真实餐品、实物餐牌、装盒、葱、油渣和叉烧形象，固定位置；上岗前有示范与任务测试。员工若无法可靠识别金额和找零，安排会核账人员负责收款，图片不能替代金钱核对能力。

**不做全站无文字模式。** 老板财务、成员权限、退款、关账保留完整中文；员工只看到岗位所需操作。自由备注依赖读写和厨师确认，不作为不识字员工的主要定制入口。

## 2. 从餐牌到6张餐品入口

| 图片入口 | 对应数据 | 固定图片 |
|---|---|---|
| 红酱面 | dry_noodle + sauce:red | 橙盘、红酱细面、叉烧与葱 |
| 黑酱面 | dry_noodle + sauce:black | 橙盘、深色黑酱细面 |
| 白酱面 | dry_noodle + sauce:white | 橙盘、浅色干捞面 |
| 云吞汤面 | soup_noodle | 深橙碗、明显汤水与面条 |
| 云吞汤 | wanton_soup | 深橙碗、汤和云吞，不出现面条 |
| 干捞云吞 | dry_wanton | 浅橙盘、无面无汤的拌云吞 |

前三张只是同一种面条的酱料快捷入口，不改变四种productKind。默认小份细面；点一次图就选择餐品及酱料，再加入本单。干捞云吞点开后只有红/黑酱图卡，依据餐牌隐藏白酱。

食物照片不直接编码份量：盘中几粒云吞容易因遮挡读错，真实数量以规格图卡的10/15和后厨精确计数为准。展示叉烧/云吞的默认餐品图用于品类识别；Kosong启用后必须切换熟净面图，不能继续保留带肉图仅靠一个小标签纠正。首版演示图谱缺熟净面图，Claude需补拍或制作独立净面资产后才可用于生产。

## 3. 面种与份量

两种面以原料实拍图显示：细黄面团/宽扁面薄；点击区至少80×80px。图片和中文「细面/面薄」位置固定。KDS每行显示同一原料缩略图，顶部将两种份团分栏合计。

小份：完整面团图×1、RM7；中份：完整面团＋半团、1½、RM9；大份：完整面团×2、RM11。不要仅用碗的大小表示份量，因为视差和照片大小会误导。小中大也保留中文，数值与配方仍由领域模型决定。

云吞规格10/15用相同云吞图＋大数字，不画15粒微小图让员工逐粒数。Kosong对应RM3.50/4.50/5.50，原份团数不变。

## 4. 图卡语义表：跨POS/KDS/培训一致

| 语义ID | 图片规则 | 短中文 | 注意事项 |
|---|---|---|---|
| `spice:none` | 一支辣椒上加红色斜杠 | 不辣 | 表示不加额外辣椒；红酱本身可能有辣味，不作无辣/无过敏承诺 |
| `spice:less` | 1支辣椒 | 少辣 | 与正常辣明确不同 |
| `spice:normal` | 2支辣椒 | 普通 | 图数量代表档位，不是实际放几支辣椒 |
| `spice:extra` | 3支辣椒 | 加辣 | 不使用火焰代替Kosong |
| `scallion:normal` | 一撮葱花 | 正常葱 | 默认可在KDS弱化，但不能完全丢失配置 |
| `scallion:extra` | 葱花＋大加号 | 多葱 | 不靠绿色深浅区别 |
| `scallion:none` | 同一葱花图＋粗红斜杠 | 走青 | 不用一片叶子代表所有蔬菜 |
| `lard:normal` | 金黄色油渣颗粒图 | 正常油渣 | 必须经员工辨认，不用猪头符号 |
| `lard:extra` | 油渣图＋大加号 | 多油渣 | 不承诺具体克数，需配厨房培训 |
| `lard:none` | 同一油渣图＋斜杠 | 无油渣 | 不等于无猪油、清真或无猪肉 |
| `addon:char_siew` | 叉烧实物图＋加号＋RM2 | 加叉烧 | 默认叉烧与额外加料区分 |
| `addon:wanton_3` | 3粒独立云吞图＋加号＋RM2 | 加3粒 | 云吞加料必须精确3粒 |
| `kosong:on` | 熟净面＋叉烧划除＋云吞划除 | 净面 | 两种肉加料锁定；不能被理解为无猪油/素食 |
| `service:dine_in` | 餐桌上放橙盘的图 | 堂食 | 用实际就餐物件，不只英文字母 |
| `service:takeaway` | 带盖餐盒放入提袋图 | 打包 | 配料图跟随整单，汤品保留汤本体 |
| `action:start` | 面篮/漏勺入锅图 | 开始制作 | 固定在卡片底部 |
| `action:serve` | 餐盘从厨房递出并有勾 | 完成出餐 | 不与收银「收款勾」使用同一上下文图 |
| `action:undo` | 左向回转箭头＋原餐牌号 | 撤回 | 30秒内、权限与牌锁约束不变 |
| `token:return` | 手把实体牌放回牌架 | 餐牌回收 | 区分出餐与实体回收 |

斜杠始终表示移除该食材，不与“禁止点击”状态混用。选中状态用粗外框＋勾选，锁定用锁＋灰色，不用把照片变红当状态。照片本身的红酱、绿色葱不能当成成功/错误状态。

## 5. 收款和连接状态也要有图

现金用纸币与硬币图，QR用真实可用收款码入口图；金额始终大字。确认前展示餐牌图、餐品缩略图、数量、应收、实收、找零。没有读账能力的员工不能仅点一张现金图就把任意单标已付。

接单进度使用三幅图：`收银设备内有订单 → 云端有勾 → 厨房屏上有原餐牌`，每幅图下方保留中文。未完成用空心/时钟；断网时云到厨房连线断开并加「手拿纸单递给厨师」图。不能靠小Wi-Fi图标和“offline”一词解释。

离线确认按钮之后，展示「24号餐牌＋订单图片＋纸单递给厨师」；员工点人工交接图才记人工已交接，仍不伪造KDS收到。主收银恢复网络后，已人工出餐单在人工区域显示“厨师已交出餐盘”，不显示新待做提醒。

退款、取消已制作、关账、处理同步冲突采用中文原因＋有权限人员确认。拒绝把破坏性动作简化成一个没有解释的垃圾桶。

## 6. 素材与离线工程契约

预览资源 `visuals/assets/food-atlas-v1.png` 为内置imagegen基于用户餐牌生成的**演示识别图谱**，不是档口实拍，不保证展示份量/配料完全等同实际售卖。3×3按行：红/黑/白面；汤面/云吞汤/干捞云吞；叉烧/细面原料/面薄原料。生成Prompt见同目录 `生成说明.md`。原始用户餐牌副本放 `visuals/references/`，价格来源仍由业务配置控制。

Claude实现时使用独立可版本化WebP/PNG资产，建立显式manifest：`photoId,version,path,hash,width,height,altZh,reviewedBy`。演示可用CSS精灵图，生产优先独立图片便于替换与差分缓存。不用图片文件名做业务ID；不把文本画死到图片里；像素图失败用稳定SVG图卡＋中文代替，界面不能变空白。

**所有营业必需图片必须随PWA壳预缓存并校验。** 开档离线检查包含图片可用性；新菜单发布先准备资源版本，旧订单图卡继续可解析。不得依赖营业时访问第三方图片CDN，也不得把所有图片base64写进订单。受信任静态图可由Hosting缓存，交易/身份请求不缓存。

首版素材需求：6餐品图、2面种图、1熟Kosong净面图、叉烧与独立云吞图、葱/油渣/辣椒图、堂食/打包、现金/QR、接单三状态、人工传单、制作/出餐/餐牌回收。缺资产按清单补齐，不能以小字号双语文字代替。

## 7. 培训卡与可用性验收

一张可打印A4/A3训练卡：上半部6餐品对照＋两面种，下半部辣度、葱、油渣、净面、加料、出餐/回收。使用与软件同一素材和位置；由老板用员工熟悉的口语示范，不假定识字或符号理解。

至少找2名符合目标语言背景的实际/代表员工，先示范约10分钟，然后不依赖读中英完成12个情境：红酱小面；黑酱中面薄；白酱大面；汤面；云吞汤；干捞云吞；少辣走青；多油渣；加3粒；Kosong；打包；离线人工交接。额外测试KDS辨认同图、区分两种面、出餐及餐牌回收。

目标：普通题首轮独立正确率≥90%，Kosong肉类移除、面种、汤品打包保留汤、是否已付款、是否真正送到厨房等关键题不得出现未纠正的严重误解。记录错误/求助/耗时，不以“看起来直观”代替验证；未达标修改图片或流程并复测。此为产品验收目标，不声称未测试即达到。

触区≥56px、核心图片≥80px、KDS特殊图卡≥48px并在1.5米检查；不靠悬停才出现说明。对无图片/色弱/弱视仍提供文字、焦点与读屏标签；读屏与图片优先并不冲突。
